# Broker API Adapter Pattern

This module implements a broker-agnostic adapter pattern allowing CROCODILE to switch between different Zerodha authentication methods without changing business logic.

## Architecture

```
                    ┌─────────────────────┐
                    │   BrokerAdapter     │  (Abstract Interface)
                    │   broker_adapter.py │
                    └──────────┬──────────┘
                               │
              ┌────────────────┴────────────────┐
              ▼                                 ▼
    ┌──────────────────┐            ┌──────────────────┐
    │ EnctokenAdapter  │            │  KiteAPIAdapter  │
    │ enctoken_adapter │            │ kite_api_adapter │
    │   (original)     │            │   (new - SNAIL)  │
    └──────────────────┘            └──────────────────┘
                    ▲                         ▲
                    └────────────┬────────────┘
                                 │
                    ┌────────────┴────────────┐
                    │    broker_factory.py    │
                    │  get_broker() function  │
                    └─────────────────────────┘
```

## Files

| File | Description |
|------|-------------|
| `broker_adapter.py` | Abstract base class defining all broker operations |
| `enctoken_adapter.py` | Wraps existing KiteTradeClient (enctoken method) |
| `kite_api_adapter.py` | Uses official kiteconnect library with SNAIL's token |
| `broker_factory.py` | Factory function to create appropriate adapter |
| `kite_trade_client.py` | Original enctoken-based client (unchanged) |

## Usage

### In Services/Workflows

```python
# Old way (direct client usage)
from src.api.kite_trade_client import KiteTradeClient
kite = KiteTradeClient()

# New way (adapter pattern)
from src.api.broker_factory import get_broker
broker = get_broker()  # Returns appropriate adapter based on config
```

### Configuration

In `config/config.yaml`:

```yaml
kite:
  # Choose authentication method
  trade_method: "kite_api"  # Options: "enctoken" | "kite_api"

  # Enctoken settings (used when trade_method: "enctoken")
  token_file: "../data/enctoken.txt"

  # Kite API settings (used when trade_method: "kite_api")
  kite_api:
    token_file: "../data/kite_access_token.json"
    validate_token_date: true
```

## Trade Methods

### 1. Enctoken (Original)
- Uses web scraping to get encrypted session token
- Requires credentials in `.env` or `config.yaml`
- CROCODILE handles its own authentication
- Token stored in `enctoken.txt`

### 2. Kite API (New - Recommended)
- Uses official Kite Connect API
- Token generated by SNAIL bot at 8:45 AM
- No credentials needed in CROCODILE
- Token stored in `kite_access_token.json`

## Token Generation

For `kite_api` method, token can be generated two ways:

1. **SNAIL Morning Startup** (automated on Pi):
   ```bash
   cd SNAIL && python main.py startup
   ```

2. **Standalone Script** (manual):
   ```bash
   cd CROCODILE && python generate_kite_token.py
   ```

## Switching Methods

To switch from `kite_api` to `enctoken`:

1. Edit `config/config.yaml`:
   ```yaml
   kite:
     trade_method: "enctoken"
   ```

2. Restart CROCODILE workflows

No code changes required - the factory pattern handles it automatically.

## Cron Schedule Compatibility

| Job | Time | Token Ready? |
|-----|------|--------------|
| SNAIL token generation | 8:45 AM | - |
| CROCODILE morning startup | 9:00 AM | ✓ (15 min buffer) |
| Signal processing | 9:15 AM+ | ✓ |

## Error Handling

Morning startup validates token before trading:
- Checks token file exists
- Validates token was generated today
- Sends Telegram alert if token is invalid
- Falls back gracefully with clear error messages
